# 상시 팀 에이전트와 임시 서브에이전트 실행 설계

> 이 문서는 **목표 계약**이다. 스킬을 설치하거나 흐름 화면을 켠 것만으로 아래의 실행 추적·잠금·복구가 자동으로 활성화되지는 않는다.

## 두 종류의 작업자

| 구분 | 상시 팀 에이전트 | 임시 서브에이전트 |
| --- | --- | --- |
| 수명 | 여러 프로젝트에 걸쳐 유지 | 한 작업 또는 검증 범위에 한정 |
| 배정 | 역할·부하·권한으로 담당자를 결정 | 담당자/총괄이 범위가 좁은 병렬 조사·구현·독립 검증을 위해 생성 |
| 책임 | 프로젝트의 작업 카드와 산출물에 대한 책임 | 부모 작업에 제출물을 돌려주는 실행자; 프로젝트의 최종 책임자가 아님 |
| 식별 | 안정적인 `agentId` | 매번 새 `executionId`, `runId`, `childSessionKey` |

한 전문 작업은 여러 번 재시도될 수 있고, 한 실행에서 여러 자식이 파생될 수 있다. 따라서 **작업(`taskId`)과 실행(`executionId`)을 분리**한다. 서브에이전트를 독립 프로젝트나 새 책임자로 자동 승격하지 않는다.

## 단일 원장과 관계

```text
사용자 요청(sourceRef) → 프로젝트/Run(runId)
  → 작업(taskId, ownerAgentId, dependsOn[], acceptanceCriteria[])
    → 실행(executionId, runtime, parentExecutionId?, parentSessionKey?,
            childSessionKey?, runtimeRunId?, depth, permissionScope, deadline)
      → 제출(artifactVersion, evidenceRefs[])
        → 독립 검수(reviewDecision, reviewerAgentId, criteriaResults[])
          → 총괄 통합(integrationDecision, deliveryReceipt?)
```

`taskId`가 권위 있는 업무 키이고 OpenClaw 세션은 실행 참조다. 세션 목록 또는 완료 메시지 자체를 업무 원장으로 삼지 않는다. `sessions_spawn`의 접수 응답에 있는 `runId`·`childSessionKey`는 **실행 시작 접수증이지 완료 증거가 아니다**. 부모가 끝나도 자식이 살아 있을 수 있으며 자식이 다시 자식을 만들 수도 있으므로 `parentExecutionId`와 `depth`를 보존한다.

## 디스패치와 수집

1. 총괄이 목표, 완료 기준, 승인 경계, `sourceRef`를 정하고 동일 요청 멱등키로 Run을 생성한다.
2. 작업 DAG의 순환·고아·권한을 검사한다. 선행 작업의 **검수 통과** 전에는 후속 작업을 `ready`로 승격하지 않는다.
3. 실행 레코드를 `queued`로 먼저 기록하고 lease를 잡는다. OpenClaw spawn에 `taskId`·`executionId`·산출물 형식·허용 범위·기한을 전달한다.
4. 접수 응답의 `runId`·`childSessionKey`를 해당 실행에 저장하고 `accepted/running`을 구분한다. 접수 실패·타임아웃은 작업을 조용히 `done`으로 만들지 않는다.
5. 완료 이벤트 또는 결과 수집 시 원본 실행 ID와 산출물 버전을 검증하고 `submitted`로 기록한다. 부모 에이전트가 자식 결과를 요약해 전달해도 원본 실행 참조를 잃지 않는다.
6. 별도 검수자가 기준별 근거로 `pass/changes_requested`를 판정한다. 반려 시 의존하는 후속 결과를 `stale`로 표시한다. 총괄만 통합·사용자 전달 완료를 선언한다.

모델이 직접 `sessions_spawn`을 호출할 수 있다면, 래퍼/도구 훅이 실행 접수증을 기록하거나 총괄이 같은 턴에 등록해야 한다. 기록되지 않은 자식은 대시보드에 `미연결 실행`으로만 표시하고, 프로젝트 작업인 것처럼 추측해 붙이지 않는다.

## 실패·권한·재조정

- 실행별 허용 도구·파일/서비스 범위·외부 부작용·예산·최대 depth·동시 실행 수를 기록한다. 런타임의 기본 도구 제한만으로 쉘을 통한 부작용까지 통제됐다고 가정하지 않는다.
- `queued → accepted → running → submitted | failed | timed_out | cancelled`를 실행 상태로 둔다. 작업의 `accepted/integrated`는 **검수/통합 상태**이므로 실행의 `accepted`와 혼동하지 않는다.
- 일정 간격으로 실제 세션 상태와 실행 원장을 재조정한다. 만료 lease, 부모 종료 뒤 남은 자식, 접수됐지만 시작하지 않은 실행을 총괄에게 올린다. 의도적으로 취소된 자식은 자동 재시작하지 않는다.
- 외부 발송·구매·게시·배포는 재시도 전에 실제 결과와 전달 영수증을 조회한다. 불확실한 부작용은 자동 재실행하지 않는다.
- 동일 `sourceRef`/작업/시도에는 멱등키를, 이벤트에는 단조 증가 버전을 둔다. 중복 완료 이벤트는 한 번만 반영한다.

## 대시보드 수용 기준

프로젝트 → 작업 → 실행(상시 담당/임시 자식/중첩 자식) → 제출 → 검수 → 통합을 각각 별도 축으로 보여준다. 실행 행에는 상태, 실제 시작·종료 시각, 부모, 런타임, 근거 링크, 실패/재시도 여부를 표시한다. 세션 ID가 없으면 `실행 미연결`, 검수 증거가 없으면 `검수 미기록`, 전달 영수증이 없으면 `전달 미확인`으로 표시한다. 오래된 `done` 카드들을 소급해 QA 통과로 칠하지 않는다.

최소 검증 시나리오: (1) 독립 자식 두 개를 병렬 실행하고 서로 다른 실행 ID로 결과 수집, (2) 실패한 자식 한 개만 재시도하되 같은 작업과 다른 실행 ID 유지, (3) 부모 종료 뒤 남은 자식을 고아로 감지, (4) 검수 반려 시 후속 통합 차단, (5) 중복 완료 이벤트·불확실한 외부 발송에 재실행 없음.
