# 실전 수업: AI 에이전트 오케스트레이션

대상: OpenClaw 초·중급 사용자 · 90분 표준 / 60분 축약 · 가상 데이터만 사용

## 수업 목표

수강생은 (1) 요청을 검증 가능한 완료 기준으로 바꾸고, (2) 선행·병렬 작업을 나누고, (3) 담당자의 ‘완료’와 독립 검수 ‘통과’를 구분하며, (4) 총괄의 통합·사용자 전달까지 증거를 남긴다. 에이전트 수가 많다는 사실만으로 오케스트레이션이 완성되지는 않는다.

## 강사 준비

- 총괄 1명, 조사·작성·디자인·검수 역할을 준비한다. 같은 실행 환경에서 역할을 합쳐도 되지만, 검수자는 가능하면 작성자와 분리한다.
- 각 역할의 권한과 사용할 단일 작업 원장을 정한다. 계정·토큰·고객정보는 시연 데이터에 넣지 않는다.
- [샘플 작업](../examples/product-page/sample-run.json)과 [시각화 데모](../dashboard/demo.html)를 미리 열어 둔다.
- 시연의 게시·결제·대외 발송은 가상으로 멈춘다. 실제 공개 전 승인은 사람이 결정한다.
- 사용 중인 제품의 이름을 소개하는 것과 그 제품의 소스코드를 수업 자료로 재배포하는 것은 다르다.

## 시간표

| 시간 | 진행 | 확인할 결과 |
| --- | --- | --- |
| 0–10분 | 도입: “담당자가 다 했다고 하면 바로 게시하시겠어요?” | 제출/검수/통합/전달 차이 인식 |
| 10–25분 | 총괄·전문·의존성·독립 QA·통합 설명 | 역할/상태를 본인 말로 정의 |
| 25–40분 | 가상 상세페이지 라이브 데모 | 병렬, 반려, 승인 전 정지 관찰 |
| 40–70분 | STEP 1–7 따라하기 | 작업 원장과 검수 기록 작성 |
| 70–80분 | 퀴즈·피드백 | 오류 사례 판정 |
| 80–90분 | 과제 안내·회고 | 자신의 업무에 적용할 다음 단계 |

60분 축약: 도입 5분, 개념 10분, 데모 10분, 실습 25분, 검토·과제 10분. 실습 데이터와 역할은 그대로 둔다.

## 개념: 다섯 개의 책임

1. **총괄**: 목표, 수락 기준, 작업 분해, 충돌 해결, 최종 통합과 사용자 보고의 책임자.
2. **전문 담당**: 범위가 명확한 산출물을 만들고 버전·근거·남은 위험을 제출한다.
3. **의존성**: 선행 작업이 통과해야 후행을 시작할 수 있는 강한 연결, 참고만 하는 약한 연결을 구분한다.
4. **독립 QA**: 작성자의 자기평가가 아닌 별도 기준별 합격/반려 판단을 남긴다.
5. **통합**: 합격한 산출물을 합치고 전체 동작과 실제 전달을 확인한다.

`접수 → 계획 → 작업 → 제출 → 독립 검수 → 통합 → 필요한 승인 → 실제 전달 확인`

현재 대부분의 간단한 작업 보드는 `일정/확정/진행/완료` 정도만 기록한다. `완료` 하나를 위의 모든 단계로 해석하면 안 된다.

## 라이브 데모: 가상의 텀블러 상세페이지

브랜드 ‘솔담’, 보온 텀블러 450ml, 가격 29,000원은 모두 가상의 수업 데이터다.

- A 조사: 제품 사양·가격 근거 목록 작성. 총괄이 근거를 확인한다.
- A 통과 뒤 B 문구와 C 디자인 가이드를 병렬로 진행한다. B와 C의 좌우 배치는 실행 순서를 뜻하지 않는다.
- B와 C가 모두 통과한 뒤 D 상세페이지 조립을 시작한다.
- E 독립 QA에서 요약표가 28,000원, 본문이 29,000원인 충돌을 찾는다. B를 반려하고 수정 버전을 제출받는다. 변경 전 D/E 판정은 재검토 대상으로 표시한다.
- 총괄이 재검수 결과를 합친다. 실제 게시 버튼을 누르기 전 사람의 승인을 받으며, 수업에서는 게시하지 않는다.

강사 질문: “B 담당자가 수정했다고 쓰면 E의 합격은 자동으로 유지되나요?” 정답: 아니다. 수정 버전의 근거와 영향을 다시 확인해야 한다.

## 따라하기: STEP 1–7

### 1. 요청 정규화

```text
다음 목표를 한 문장으로 요약하고, 사용자가 직접 확인할 수 있는 완료 기준 3개와 하지 않을 일 2개를 써줘.
목표: 가상의 텀블러 상세페이지 시안 만들기.
실제 게시·결제·고객 데이터 사용은 금지한다. 불명확한 것은 가정과 확인 필요를 분리해.
```

### 2. 역할과 권한 기록

총괄·조사·작성·디자인·QA를 정한다. 각 역할의 파일/도구 접근 범위와 외부 행동 금지선을 기록한다. 에이전트 고유 이름은 수강생 환경에 맞춰 바꾼다.

### 3. 작업 분해·의존성 표시

```text
완료 기준을 충족하는 5~7개 작업으로 분해해. 각 작업에 한 책임자, 입력, 제출물, 검수 기준, 선행 작업 ID를 적어.
병렬 가능한 작업은 분리하고, 선행 검수 전에 시작하면 안 되는 작업은 hard dependency로 표시해.
총괄 통합과 독립 QA를 별도 작업으로 남겨.
```

작업 카드를 만들었다는 것과 담당자가 실행을 시작했다는 것은 다르다. 확인·시작·제출 기록을 구분한다.

### 4. 전문 작업 위임

```text
작업 B를 작성 담당에게 위임해. 입력은 검수된 A 버전이고, 산출물은 제목/핵심 문구/가격 표기다.
제출할 때 근거, 파일/버전, 스스로 확인한 항목, 남은 위험을 함께 보고하게 해.
작업 원장에 실제 시작과 제출을 기록해.
```

### 5. 독립 검수

```text
작성자가 아닌 QA 담당이 제출 버전의 가격·사양·표기 일관성을 기준별로 검사해.
각 기준에 합격/반려와 재현 가능한 증거를 적고, 하나라도 반려면 통합 가능으로 표시하지 마.
```

### 6. 반려·재작업

28,000원/29,000원 충돌을 의도적으로 넣어 본다. 반려 사유, 수정 책임자, 재개 조건, 재검수 결과를 기록한다. 선행 산출물이 바뀌면 영향을 받은 후행 산출물을 다시 확인한다.

### 7. 총괄 통합·보고

```text
합격한 최신 버전만 합쳐. 전체 완료 기준을 다시 확인하고, 미확인 항목과 실제로 전달된 항목을 분리해 보고해.
사람 승인이 필요한 실제 게시 단계에서는 멈춰. 수업 실습에서는 외부에 아무것도 보내지 마.
```

## 운영 체크리스트

- 넘기기 전: 목표·완료 기준·책임자·입력 버전·의존성·권한 경계가 있는가?
- 받았을 때: 담당자가 시작을 확인했고, 산출물과 검증 방법을 제출했는가?
- 합친 뒤: 독립 QA 근거, 최신 버전, 전체 동작, 실제 전달 영수증이 있는가?
- 빨간 줄: 단순 `done`을 QA 통과로 바꾸지 않는다. 선행 변경을 무시하지 않는다. 실패한 외부 행동을 무조건 재시도하지 않는다. 막힌 작업을 이유 없이 닫지 않는다.

## 퀴즈

1. 작업 카드만 생성되고 담당자 시작 기록이 없다. “협업이 시작됐다”고 보고할 수 있는가? **아니오.**
2. 조사 A가 통과했고 문구 B·디자인 C에 서로 의존성이 없다. 순차 실행해야 하는가? **아니오, 병렬 가능.**
3. 작성자가 자기 결과에 `done`을 눌렀다. QA 통과인가? **아니오.**
4. B의 가격이 바뀌었다. 이미 통과한 조립 D와 QA E는? **영향 범위 재검증.**
5. 게시 API 호출이 타임아웃됐다. 즉시 재시도하는가? **아니오, 실제 게시·영수증 확인 후 중복 방지.**

## 과제와 평가 기준

제출물: 목표·완료 기준 3개, 역할/권한표, 5개 이상 작업과 명시적 의존성, 병렬 구간, 제출물 1개, 독립 QA 판정과 증거, 반려/재작업 시나리오, 총괄 통합 보고. 실제 고객 데이터·인증정보는 포함하지 않는다.

| 항목 | 점수 |
| --- | ---: |
| 목표·수락 기준의 검증 가능성 | 15 |
| 역할·권한·한 작업 한 책임자 | 15 |
| 의존성·병렬·차단 처리 | 20 |
| 제출 버전과 독립 QA 증거 | 20 |
| 반려 후 영향·재검증 | 15 |
| 통합·승인·전달 구분 | 15 |

합계 100점. 비밀정보/실제 고객정보 노출, 무승인 외부 게시, 검수 근거 없는 합격 표시는 점수와 별개로 실습 재제출 사유다. 과제 제출처와 피드백 주기는 강사가 수업 환경에 맞춰 정한다.

## 지금 가능한 것과 추가 개발이 필요한 것

**현재 일반적인 구성에서 가능한 것:** 작업 카드·담당·상태·메시지 기록, 규칙형 자동 배정, OpenClaw의 에이전트 위임·세션/자동화 기록, 총괄이 프롬프트와 작업 원장을 사용해 수동으로 분해·검수·통합하는 절차. 제공된 대시보드 예시는 기록된 작업을 읽기 전용으로 시각화한다.

**이 키트만 설치해서 자동으로 생기지 않는 것:** 데이터베이스가 강제하는 DAG 잠금, 제출/합격/통합 상태의 서버 전이, 산출물 버전 무효화, 작업 카드와 실제 실행 ID 연결, 내구성 있는 재시도·중복 방지, 외부 게시 승인 토큰. 이는 [구조 설계](architecture.md)의 후속 구현 단계다.

## 강사용 Q&A

- **한 명의 에이전트만 있는데요?** 역할을 논리적으로 분리해 시작할 수 있다. 다만 고위험 검수는 가능하면 별도 실행/사람에게 맡긴다.
- **어떤 오케스트레이션 제품을 설치해야 하나요?** 먼저 현재 OpenClaw·작업 원장으로 데모 가능한 범위를 확인한다. 새 서버를 추가하면 상태 원장이 두 개가 되지 않도록 설계한다.
- **대시보드의 선이 안 보이는데요?** `dependsOn` 기록이 없으면 선을 만들지 않는 것이 정확하다.
- **완료 보고는 언제 하나요?** 담당자 제출, QA 합격, 총괄 통합, 실제 전달을 구분한 뒤 해당 범위까지만 보고한다.
